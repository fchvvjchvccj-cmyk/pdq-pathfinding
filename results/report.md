# 原版 PDQ 实测

这轮测试想知道原版 PDQ 能不能稳定找到最短路，和现有实现比又能省多少时间。五种实现算出的最短距离和无解判定都与 BFS 一致。速度要看地图：在两张迷宫图上，BFS 的中位耗时都低于 PDQ。
## 怎么测的

用 Windows 11（10.0.22631）和 Python 3.14.7，随机种子固定为 20261103。先检查 12,484 个小图问题，再用七张公开地图和八张合成地图测耗时。每张图取 16 个查询，其中无路可走的查询也算在内。对同一查询，每种实现预热后正式计时 5 次；这些运行按随机顺序交错进行。所有查询都用 BFS 核对最短距离。

计时从初始化查询数组开始，到还原出完整路径结束。下载、解析地图、选取问题、校验结果和写文件都在计时之外。测试在单进程中串行运行，计时时关闭循环垃圾回收。CPU 频率和进程亲和性没有固定，数值会随运行环境波动。

## 配对比较

240 个查询里有 32 个无解，一共记录了 6,000 次正式计时。与高 `g` 优先的堆 A* 相比，PDQ 有 228 个查询更快，逐查询加速比的中位数是 1.673×，几何平均是 1.616×。换成桶队列 A* 作对照，中位数是 1.126×。比值大于 1 表示 PDQ 更快。

## 怎么理解这组结果

PDQ 和桶队列 A* 在同一优先级内的处理顺序相同。这 240 个查询里，两者走出的路径和扩展的节点数都一样，耗时差主要体现了队列实现的开销。各方法共用网格与数组布局，带启发值的实现还共用搜索循环。两种堆 A* 在 `f` 相等时分别优先较大或较小的 `g`；这会改变扩展量，所以表里把两者分开列，主要用较大 `g` 优先的版本作对照。

测试只复用公开场景的起点和终点，参考距离由四方向 BFS 重新计算。结果只代表抽到的地图和这里的 Python 实现；没有覆盖完整公开测试集、JPS4、KIA*、C++ 实现、多代理寻路、动态障碍或非均匀权重。
