# PDQ Pathfinding

简体中文 · [English](README.en.md)

PDQ（势差双端队列）用一个双端队列在网格里找最短路。地图可以有障碍，但搜索期间不能变；每次只能往上下左右走一格，每步代价都是 1。仓库里有 Python 实现，也有和 BFS、堆 A*、桶队列 A* 的对照结果。

## 为什么一个双端队列就够了？

从 A* 的优先级看，这个做法很好理解：朝终点走一步，已走的步数 `g` 加 1，到终点的曼哈顿距离 `h` 减 1，所以 `g + h` 不变。反过来，走远一步，`g + h` 就加 2。

PDQ 把这个变化量除以 2，将边 `u → v` 的代价写成 `(1 + h(v) - h(u)) / 2`。这样就只剩 0 和 1 两种代价。找到到达某个邻居的更短走法时，代价为 0 就把它放到队首，代价为 1 就放到队尾。这正是 0–1 BFS 的队列规则。

为什么这样算还能找到最短路？把一条路径上各步的新代价加起来，中间格子的 `h` 会抵消，最后只剩步数的一半和一个由起终点决定的常数。只要起终点不变，新代价最小的路线也就是步数最少的路线。

## 实测表现

原版 PDQ 和桶队列 A* 在实测中走出了相同的路径，扩展节点数也一样。两者的耗时差主要来自维护队列和优先级的开销。BFS 在几张需要大幅绕行的图上反而更快。

在 15 张地图的 240 个查询上，`pdq_fast` 相比原版 PDQ 的加速比中位数是 **1.43×**，相比优先较大 `g` 的堆 A* 是 **2.52×**，相比桶队列 A* 是 **1.63×**。这些数字按同一查询的耗时逐个比较后取中位数，计时包含完整路径还原。

地标版借用了 ALT 的思路。在复测的两张迷宫图上，相比直接用 `pdq_fast`，大约要查 11 次和 12 次才够摊平预处理开销。把 15 张图都算上，每张图查 16 次，仍是 `pdq_fast` 的总耗时更低。
